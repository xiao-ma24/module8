# 认证接入说明（DBA 统一登录）

> 适用版本：`school-material-dba`（DBA 集成交付版）
> 目标：业务系统**不再自建登录与令牌**，统一由 DBA 认证中心完成登录并下发身份。



## 0. DBA 2026-11-27 约定（已实现）

统一登录只传两个字段，由 DBA 保证：

| 请求头 | 含义 |
| --- | --- |
| `X-DBA-USER-ID` | 工号（= `mat_sys_user.person_no`） |
| `X-DBA-ROLE` | 角色编码（取值见《身份权限矩阵》） |

**部门不再从 `X-DBA-BUSINESS-ID` 取**，改为后端按工号查本组用户表：

```sql
SELECT org_id FROM mat_sys_user WHERE person_no = ? AND del_flag = 0 LIMIT 1
```

实现位置：各模块 `security/CurrentUserServiceImpl.orgIdOf(userNo)`，组装 `new CurrentUser(userNo, role, orgId)`。
`X-DBA-BUSINESS-ID` 仅保留过渡期兼容（查库为空时才回退），验收后关闭。

> 影响：集成后 DBA 只需下发工号与角色；部门、仓库等业务归属由本组自行按工号查表得到。

## 1. 统一身份契约

所有业务代码获取“当前用户”只允许调用一个入口：

```java
// 6 个后端各自的 security 包下
CurrentUserService.current();        // 未登录直接抛 401
CurrentUserService.currentOrNull();  // 未登录返回 null，由调用方自行决定
```

`CurrentUserService` 是**接口**，当前实现类为同包下的 `CurrentUserServiceImpl`（`@Service`）。
DBA 集成时只需替换该实现类（如改为校验统一登录令牌 / 调用 SDK），业务代码无需改动。

返回对象（6 个模块定义完全一致）：

```java
public record CurrentUser(String userId, String role, String businessId) {}
```

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| `userId` | 用户标识 | 字符串，兼容 DBA 的 SSO subject / 工号；演示数据里为 `mat_sys_user.user_id` 的数字串 |
| `role` | 角色编码 | 取值见《身份权限矩阵》，DBA 需把自有角色映射到 8 个编码 |
| `businessId` | 业务归属 | 部门 ID / 仓库 ID 等，可空；用于数据范围控制 |

> 该签名与《给各组的接入通知》§2.1 的 `CurrentUser(String userId, String role, String businessId)` 完全一致。

## 2. 身份传递方式（当前预留实现）

`CurrentUserService` 按以下顺序解析身份，任一种生效即可：

1. 请求头 `X-DBA-USER-ID`（工号）+ `X-DBA-ROLE`（角色）；`X-DBA-BUSINESS-ID` 仅过渡期回退使用
2. Cookie `DBA_TOKEN`（值即用户标识字符串，对应 `CurrentUser.userId`）
3. 课程演示登录态（`AuthContext` 内存令牌，仅 00/03/04 存在，接入后删除）

以上名称均可在 `application.yml` 或环境变量中修改：

| 配置项 | 环境变量 | 默认值 |
| --- | --- | --- |
| `auth.identity-cookie-name` | `AUTH_COOKIE_NAME` | `DBA_TOKEN` |
| `auth.identity-user-header` | `AUTH_USER_HEADER` | `X-DBA-USER-ID` |
| `auth.identity-role-header` | `AUTH_ROLE_HEADER` | `X-DBA-ROLE` |
| `auth.identity-business-header` | `AUTH_BUSINESS_HEADER` | `X-DBA-BUSINESS-ID` |

> **待 DBA 确认**：Cookie 名称、令牌格式（明文 / JWT / 加密串）、是否需要回调认证中心校验、
> 网关是否直接注入身份头。确认后只需替换各模块 `CurrentUserService.currentOrNull()` 的实现，
> 业务代码零改动。

## 3. 登录 / 未登录 / 无权限约定

| 场景 | 约定 | 当前实现 |
| --- | --- | --- |
| 未登录访问受保护接口 | HTTP **401** | 6 个模块的 `IdentityInterceptor` 统一返回；演示模式仍由各组登录拦截器返回业务码 401 |
| 已登录但无权限 | HTTP **403** | `@RequireRole` 声明角色，拦截器校验不符即返回 403 |
| 登录成功 | DBA 写 Cookie，业务系统不签发令牌 | 预留 |

> **统一鉴权已实现，由 `AUTH_ENFORCE` 开关控制**（默认 `false`）：
> - `AUTH_ENFORCE=true`：未取得 `CurrentUser` → HTTP 401；命中 `@RequireRole` 且角色不符 → HTTP 403
> - 白名单：`/auth/**`、`/swagger`、`/v3/api-docs`、`/error`、`/actuator`，以及子系统② 的 `/purchase/inventory/**`（③④⑤ 内部库存调用，内部凭证留待 P1）
> - 默认 `false` 时保留各组演示登录（`X-Token` / `handoff`），本地开发不会被拦
> - 角色注解分布：00 管理端 `ADMIN`；01 维护类接口 `ADMIN`；02 审批 `DEPT_HEAD`、验收 `CHECKER/STORE_KEEPER`、入库与订单 `STORE_KEEPER/PURCHASER`；03 审批 `DEPT_HEAD`、出库 `STORE_KEEPER`；04 审批 `DEPT_HEAD`、借出归还报损 `STORE_KEEPER`；05 盘点/预警 `STOCKTAKER`、补货审批 `PURCHASER`
>
> 开启方式：`AUTH_ENFORCE=true bash scripts/start-all.sh`

  其余 00/01/03/04/05 各自独立站点（5180/5173/5183/5184/5185），由 DBA 统一前端按模块跳转进入。
- 前端附加凭证的位置（页面代码不出现令牌，凭证由浏览器按同源自动携带）：
  1. 02：`src/shared/http.js` —— 5 个业务模块（通用 / 基础数据 / 领用 / 借用 / 盘点）共用的唯一 axios 实例，已开 `withCredentials: true`，统一处理 401
  2. 01：`src/utils/request.js` —— 已开 `withCredentials: true`
  3. 00 / 03 / 04：各自的 `src/api/index.js` —— 已处理业务码 401 并跳转本组登录页；未显式设置 `withCredentials`，同源部署下浏览器默认携带 Cookie
  4. 05：`src/api/index.js` —— 同 00/03/04，同源部署下默认携带 Cookie
- 401 处理：后端返回未登录时，前端跳转登录地址（当前保留各组演示登录页，接入后改为 DBA 统一登录地址配置项）。
- 构建产物：`dist/frontend`（02 统一大系统）与 `dist/frontend-m00/m01/m03/m04/m05`，由 `npm ci && npm run build` 生成（命令见《部署与启动说明》§4）。

## 6. 安全建议

1. Cookie 建议 `HttpOnly; Secure; SameSite=Lax; Path=/`，生产必须 HTTPS。
2. 业务服务只信任网关下发的身份头，**不要**把 8080~8085 直接暴露到公网。
3. 禁止前端自行拼接 `userId` 作为身份依据（02 已做兜底兼容）。
4. 接入后关闭 Swagger UI 或限制为内网访问。
